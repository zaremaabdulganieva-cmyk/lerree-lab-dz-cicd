Уязвимых зависимостей нет (`npm audit`: 0). Две серьёзные проблемы были не в коде приложения, а в настройках доступа в базе. Их нашла только ручная проверка «а что можно сделать с публичным ключом», а не автоматический сканер.

## Как проводился аудит

1. **Зависимости** — `npm audit` (и в CI при каждом пуше: `npm run audit:deps`, падает на уровне high и выше). Dependabot еженедельно открывает PR с обновлениями.
2. **Код по OWASP Top 10** — ИИ-агент (Claude Code) прочитал весь слой данных (`src/lib/*`), серверную функцию (`api/*`), миграции и политики доступа, CI-конфигурацию. Задание агенту:
   > Проведи аудит безопасности по OWASP Top 10 (2021). Для каждой категории: что в проекте ей подвержено, есть ли проблема, как проверить на практике. Особое внимание — что может сделать посторонний, у которого есть только публичный anon-ключ и опубликованный демо-пароль. Каждую находку подтверди запросом к живой базе, не ломая данных.
3. **Проверка на живой базе** — запросы `curl` к Supabase с публичным ключом, как это сделал бы посторонний.

## Найденные проблемы и исправления

### SEC-01 · Высокий · Любой зарегистрировавшийся получал платный контент (A01 Broken Access Control)

**Что было.** Регистрация в Supabase открыта: `GET /auth/v1/settings` → `"disable_signup": false`. При регистрации триггер создаёт карточку профиля, а в таблице `profiles` по умолчанию стояло `subscription_status = 'active'` и `subscription_until = сегодня + 30`. Кто угодно мог вызвать `supabase.auth.signUp()` с публичным ключом, подтвердить свою почту — и получить доступ ко всем программам и материалам на месяц.

**Почему не просто закрыть регистрацию.** Вход через Google (шаг 3 задания) создаёт новых пользователей тем же путём: с закрытой регистрацией он не заработает.

**Исправление** (`supabase/migrations/006_security_fixes.sql`): новая карточка создаётся с истёкшей подпиской — и значениями по умолчанию, и явно в триггере `handle_new_user`. Доступ открывает только администратор. Новичок попадает на экран «подписка истекла», как и в настоящем клубе до оплаты.

### SEC-02 · Высокий · Посетитель мог сменить пароль демо-доступа (A07 Identification and Authentication Failures)

**Что было.** Демо-пароль опубликован в README для проверяющего. Войдя с ним, можно вызвать `PUT /auth/v1/user` с новым паролем — и следующий проверяющий в кабинет уже не попадёт. Проверено безопасно: попытка «сменить» пароль на тот же самый дошла до сравнения паролей (`422 same_password`), то есть смена на другой прошла бы.

**Исправление** (миграция 006): триггер `demo_accounts_guard` на `auth.users` запрещает менять пароль и почту у `anna@demo.ru` и `olga@demo.ru`. Запрет стоит в базе, обойти его из браузера нельзя.

### SEC-03 · Средний · Не было заголовков безопасности (A05 Security Misconfiguration)

**Что было.** Сайт отдавался без Content-Security-Policy и защиты от встраивания в чужой `<iframe>`. Сессия Supabase хранится в `localStorage`, поэтому любая XSS сразу означала бы кражу входа — CSP здесь главный рубеж.

**Исправление** (`vercel.json`, раздел `headers`):
- `Content-Security-Policy` — скрипты только свои. Стили — свои и Google Fonts, шрифты — с `fonts.gstatic.com`. Запросы — только к себе и в Supabase. Встраивание запрещено (`frame-ancestors 'none'`), плагины тоже (`object-src 'none'`).
- `X-Frame-Options: DENY` — защита от кликджекинга для старых браузеров.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.
- `Permissions-Policy` — выключены камера, микрофон, геолокация, оплата.
- HSTS Vercel добавляет сам (`max-age=63072000; includeSubDomains; preload`).

`'unsafe-inline'` для стилей оставлен сознательно: React и Tailwind задают часть стилей прямо в разметке, а внедрить скрипт через стиль нельзя.

### SEC-04 · Низкий · Функции проверки прав вызывались без входа (A01)

**Что было.** В Postgres функции по умолчанию доступны всем. Гость мог вызвать `POST /rest/v1/rpc/is_admin` с любым идентификатором и узнать, администратор ли это. Проверено: ответ `false` без входа.

**Исправление** (миграция 006): право вызова `is_admin` и `is_active_member` отозвано у `public` и `anon`, оставлено только вошедшим (`authenticated`) — политикам доступа этого достаточно.

### SEC-05 · Низкий · Проверка здоровья раскрывала текст внутренних ошибок (A05)

**Что было.** `/api/health` открыт всем и при сбое возвращал сырое сообщение: например, `getaddrinfo ENOTFOUND <хост>`.

**Исправление** (`api/health.ts`): наружу уходит только «проверка упала / прошла» и время ответа. Полный текст ошибки пишется в журнал Vercel. Добавлен тест `текст ошибки остаётся в журнале и не уходит наружу`.

### SEC-06 · Низкий · Уязвимость в `undici` (A06 Vulnerable Components) — найдена 30.09

**Что было.** Новое предупреждение GHSA-rx4f-c7p8-82vq: DoS через WebSocketStream в `undici@7.29.0`. Появилось уже после аудита, нашлось при очередной установке пакетов. `undici` приходит через `jsdom` — он нужен только тестам. В браузер и на Vercel эта библиотека не попадает, поэтому проверка в CI (`--omit=dev`) её не показала.

**Исправление.** `npm audit fix` — `undici@7.30.0`, 0 уязвимостей.

**Вывод.** Проверка в CI смотрит только то, что уходит на сайт, — это правильно для блокировки выкладки. Но инструменты разработки тоже стоит проверять. Сейчас это делает Dependabot раз в неделю.

## Что проверено и в порядке

- **XSS (A03).** React экранирует всё, что выводит. В коде нет `dangerouslySetInnerHTML`, `innerHTML`, `eval`, ссылок из пользовательских данных. Плюс CSP.
- **SQL-инъекции (A03).** SQL-запросы в приложении не собираются: всё идёт через PostgREST с параметрами. Ограничения `check` в базе дублируют проверку формы.
- **CSRF.** Не применимо: вход передаётся заголовком `Authorization: Bearer`, а не cookie. Чужой сайт не может отправить запрос от имени участницы.
- **Доступ к чужим данным (A01).** RLS включён на всех 7 таблицах. Замеры и подходы видны только владелице. Роль и подписку участница поменять не может (триггер `guard_profile_fields`). Представление `last_workout_sets` работает с `security_invoker`, поэтому политики действуют и через него. Всё это покрыто 12 проверками в `scripts/check-rls.sql`.
- **Секреты (A02).** Секретный ключ `service_role` в приложении не используется. Публичный ключ и адрес базы приходят из секретов CI и переменных Vercel, в git их нет. Токен Vercel — только в секретах GitHub.
- **Перебор паролей (A07).** Лимиты на вход ставит сам Supabase Auth (ответ 429). Приложение показывает понятное сообщение.
- **Зависимости (A06).** `npm audit` в CI, Dependabot еженедельно. Связанные пакеты (react + react-dom) обновляются группой, чтобы не ломать сборку.
- **Шрифты.** С 30.09 шрифт Manrope лежит на самом сайте, а не на Google Fonts. CSP стал строже: `style-src` и `font-src` — только `'self'`, Google не видит посетителей.
- **CI (A08).** У workflow права только `contents: read`, запись в PR — лишь у шага превью. PR от Dependabot секретов не получают. Версия Vercel CLI зафиксирована.

## Рекомендации (не исправлялось)

1. **Закрепить GitHub Actions по SHA коммита, а не по тегу** (`actions/checkout@<sha>` вместо `@v4`). Тег можно переписать, SHA — нет. Dependabot умеет обновлять и SHA.
2. **Включить в Supabase «Secure password change»** (Auth → Providers → Email). Смена пароля будет требовать недавнего входа. Для демо это уже закрыто триггером, для настоящего клуба пригодится.
3. **Для настоящего клуба — капча на регистрацию и вход** (Supabase поддерживает hCaptcha/Turnstile), если регистрация будет открыта публично.

## Как применить исправления

1. Миграция 006: Supabase → SQL Editor → вставить `supabase/migrations/006_security_fixes.sql` → Run.
2. Заголовки и `/api/health` выезжают сами при следующей выкладке через CI.
3. Проверка после выкладки:
   ```bash
   curl -sI https://lerree-lab-dz-cicd.vercel.app | grep -iE "content-security|x-frame|nosniff"
   ```
