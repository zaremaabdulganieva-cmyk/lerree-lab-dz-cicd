# Как AI-агент участвовал в разработке — от идеи до продакшна

Итоговый проект собран из шести домашних заданий курса и доработан. Весь код, SQL, конфигурации и
документы написаны AI-агентом **Claude Code**; человек ставил задачи, принимал решения, проверял
результат и делал всё, что требует личного доступа (пуш, ключи, кабинеты Google/Supabase/Vercel).

Ниже — по этапам из задания: где сделано, промпт, результат, проблемы и где AI пришлось поправлять.
Пометка **«дословно»** — промпт приведён как был; **«пересказ»** — исходный текст не сохранился.

Исходные репозитории этапов:

- ДЗ 1 — выбор AI-инструментов: [lerree-lab-dz-ai-tools](https://github.com/zaremaabdulganieva-cmyk/lerree-lab-dz-ai-tools)

- ДЗ 4 — frontend: [lerree-lab-dz-frontend](https://github.com/zaremaabdulganieva-cmyk/lerree-lab-dz-frontend)
- ДЗ 5 — backend: [lerree-lab-dz-backend](https://github.com/zaremaabdulganieva-cmyk/lerree-lab-dz-backend)
- ДЗ 6 и итоговый проект — этот репозиторий (версия ДЗ 6 — тег `dz6`)

## 0. Как устроена работа с агентом

- **Выбор инструмента (ДЗ 1).** Сравнили Bolt.new, Lovable, Cursor и Claude Code по 6 критериям:
  облачные конструкторы — 19/30, Cursor и Claude Code — 25/30. Выбран Claude Code: живой проект
  дорабатывается, а не создаётся заново, и нужен агент, который сам запускает команды, тесты и
  браузер. Вывод: «класс инструмента важнее бренда».
- **Правила проекта (ДЗ 2).** Файл правил на 12 пунктов: роль → контекст → стиль → ограничения →
  формат ответа. Ключевые: объяснять простым языком, останавливаться на чекпоинтах и показывать
  diff, никогда не пушить самому, секреты — только в `.env`.
- **Эксперимент «до/после» (ДЗ 2).** Одна задача (дословно): «Напиши функцию, которая форматирует
  рабочий вес подхода для показа в карточке упражнения: вес × повторы, с учётом варианта “за 2
  гантели” и “на 2 ноги”». Без правил агент выдал `utils.js` с `any` и английскими подписями —
  0 из 8 критериев. С правилами — TypeScript в нужной папке и тест — 8 из 8.
- **Шаблоны промптов.** 5 шаблонов RTCF (Role — Task — Context — Format) и цепочка
  Chain-of-Thought из 4 шагов («сначала разберись, потом предложи план, потом код»), чтобы агент
  не «бежал кодить» сразу.
- **Субагенты.** Объёмные поиски (конкуренты, сбор фактов по шести репозиториям для этого
  документа) агент отдаёт параллельным субагентам и получает только выжимку.

## 2. Разработка

### 2.1 Инициализация проекта

- **Где:** `lerree-lab-dz-frontend/development_report.md`.
- **Результат:** Vite + React 19 + TypeScript + Tailwind 4 + React Router, раскладка
  `components / pages / lib / hooks`, файл правил агента лежит в проекте с первого коммита.
- **Грабли:** сборка падала с `TS5101: Option 'baseUrl' is deprecated` — агент исправил за одну
  итерацию; на GitHub Pages прямые ссылки давали 404 — временно `HashRouter`, в ДЗ 6 после
  переезда на Vercel вернули обычные адреса.

### 2.2 Генерация компонентов

Промпт карточки упражнения (дословно, ДЗ 4):

> **Role:** Ты Senior Frontend-разработчик на React + TypeScript + Tailwind.
> **Task:** Сделай карточку упражнения с вводом рабочего веса по подходам.
> **Context:** Где разместить: src/components/ExerciseCard.tsx. Входные данные: объект упражнения
> (название, подсказка, число подходов, диапазон повторов, подходы прошлой тренировки, есть ли
> видео). Требования ТЗ 3.3: показывать значения прошлой тренировки как подсказку; принимать только
> неотрицательное число в поле веса; при обрыве связи не терять введённое и дать повторить
> сохранение.
> **Format:** Строгие типы, без any, JSDoc по-русски. Состояния loading / error / success
> обработать явно. В конце — как проверить результат.

- **Результат:** проверка ввода по строкам, подсказка «В прошлый раз…», черновик сохраняется
  при обрыве связи, общий хук `useAsync`, переключатель «Сеть: вкл/выкл» для проверки ошибок.
- **Итоговый проект — CRUD замеров.** Агент сверил требования задания с проектом и сам нашёл
  пробел: замеры можно было только добавлять. Реализовал исправление и удаление (та же форма в
  режиме «Исправить замер», удаление с подтверждением в карточке), дописал 10 тестов и проверил
  на живой базе в браузере: добавить → исправить → удалить, демо-данные вернулись к исходным.
  По ходу проверки сам заметил, что на телефоне заголовок формы уезжает под меню, и поправил.

### 2.3 Рефакторинг и оптимизация кода

- **Дублированное состояние (ДЗ 4).** Список замеров хранился в двух местах (`useState` +
  `useEffect`) и давал гонку — её поймал тест. Переписано в одно выражение
  `saved ?? data ?? []`.
- **Структура (ДЗ 4).** Линтер ругался на смешение компонентов и функций в одном файле —
  `auth.tsx` разделён, контекст вынесен в `auth-context.ts`.
- **Клиент базы (ДЗ 6).** Вместо полного `supabase-js` подключены только нужные части
  (`auth-js` + `postgrest-js`) — минус ≈ 100 КБ кода, разделы грузятся лениво (`React.lazy`).

### 2.4 Тесты

- Рост набора: ДЗ 4 — 33 → ДЗ 5 — 59 → ДЗ 6 — 92 → итоговый проект — 102 (Vitest + Testing
  Library), покрытие ~87 %, отчёт сохраняется в CI.
- Подход (дословно из постановки ДЗ 5): «Тесты не должны требовать интернета и живой базы, но
  должны проверять и удачные ответы, и отказы сервера, которые вживую поймать трудно». Экраны
  тестируются на подставном API, API — на подставном клиенте базы.
- Отдельно `scripts/check-rls.sql` — 12 проверок прав доступа на живой базе.

## 3. Backend и инфраструктура

### 3.1 Проектирование БД

Промпт (дословно, сокращён в исходном документе):

> ДЗ 5 — продолжение ДЗ 4: подними настоящую базу под этот кабинет. Прочитай `src/data/mock.ts`
> и `src/lib/types.ts`, выведи из них сущности и связи. Схема должна повторять по смыслу боевую
> базу клуба. Данные в демо-базе — вымышленные: платный контент клуба публиковать нельзя.

- **Результат:** 7 связанных таблиц (`profiles`, `programs`, `workouts`, `exercises`,
  `materials`, `measurements`, `workout_sets`), представление `last_workout_sets`, 3 триггера,
  ограничения `check` на разумные значения.
- **Где AI пришлось поправлять:** агент перенёс поле «в прошлый раз» из моков прямо в таблицу
  упражнений. Ошибку вскрыл вопрос человека «а если участниц две?» — поле заменено
  представлением. Вывод: «ассистент склонен буквально переносить структуру исходных данных».

### 3.2 SQL-схемы и миграции

- 6 миграций на чистом SQL: схема, RLS-политики, контент, демо-участницы, `health_check`,
  исправления по аудиту.
- **Грабли:** по требованию «не отдавать непроверенный SQL» агент прогнал миграции на локальном
  PostgreSQL и нашёл свою же ошибку — защитный триггер блокировал саму миграцию.
- **Общая база.** Бесплатных слотов Supabase больше нет — демо-таблицы размещены в соседнем
  проекте. Агент сверил схемы и запретил боевой (совпадают имена таблиц, публичный демо-пароль
  дал бы вход рядом с реальными участницами); строку `revoke all … from anon` сузил до своих
  таблиц, чтобы не задеть чужие; подготовил `scripts/remove-demo.sql` для уборки.

### 3.3 API

Промпт (дословно):

> Подключи кабинет к базе. Весь разговор с сервером — в одном файле, экраны про Supabase знать
> не должны. Ошибки сервера переводи на человеческий язык, но технический код не теряй — он нужен
> для разбора. Ключи только из окружения, в коде их быть не должно.

- **Результат:** CRUD через PostgREST + RLS (`src/lib/api.ts`), перевод кодов базы в понятные
  сообщения (`errors.ts`: 23505 → «запись на эту дату уже есть» и т. д.), журнал событий.
  Серверные функции Vercel: `/api/health` (проверка входа и базы, 200/503) и `/api/log`
  (приёмник ошибок браузера).
- **Итоговый проект:** `updateMeasurement` / `deleteMeasurement` — если база не вернула строку
  (замер удалён в другой вкладке или чужой), это честная ошибка, а не тихий «успех».

### 3.4 Docker и CI/CD

- **Docker:** `docker-compose.yml` поднимает локальную PostgreSQL-песочницу для проверки
  миграций (порт открыт только на 127.0.0.1).
- **CI/CD (ДЗ 6):** GitHub Actions — Prettier, oxlint, typecheck, тесты с покрытием,
  `npm audit`, сборка (~30 с) → превью на каждый PR → выкладка из `main` с повторной проверкой
  `/api/health` и сверкой версии с коммитом. Dependabot с группировкой связанных пакетов.
- **Грабли, которые решил агент:**
  - переменные Vercel с пометкой Sensitive приходили в сборку заглушкой `[SENSITIVE]` — кабинет
    собрался без базы, хотя `/api/health` был зелёным. Теперь значения берутся из секретов
    GitHub, а сборка без адреса базы останавливает выкладку;
  - два PR Dependabot ломали сборку (react без react-dom, vitest без плагина покрытия) —
    введены группы;
  - TypeScript 7 отклонён: у него нет программного интерфейса, через который Vercel собирает
    серверные функции.

## 4. Отладка и оптимизация

### 4.1 Анализ ошибок

- **По скриншотам (ДЗ 4).** Агент сам открывал браузер и читал консоль: «60.8 кг» →
  русский формат «60,8 кг», хвост «г.» в датах убран.
- **По журналу (ДЗ 6).** Три готовых промпта в `docs/log-analysis/` — «разбор инцидента»,
  «подозрительная активность», «регрессия после выкладки». Начало первого (дословно): «Ты —
  дежурный инженер веб-приложения “кабинет участницы” (React на Vercel + Supabase …). Ниже
  сводка и журнал в JSON…». AI свёл 6 записей в один инцидент и отделил штатные ситуации.
- **Где AI ошибся:** гипотезу «двойной клик сохраняет замер дважды» он сам пометил «проверить»;
  человек проверил код — кнопка уже блокируется на время сохранения, гипотеза отклонена.

### 4.2 Производительность

Lighthouse, мобильный профиль, до → после:

- Performance 78–86 → 99; первая отрисовка (FCP) 3,2–3,9 с → 1,6 с;
- Accessibility 91 → 100, SEO 91 → 100, Best Practices 100;
- JS на странице входа 147 → 118 КБ (gzip), запросов к чужим серверам 3 → 0.

Что сделано: облегчённый клиент базы, ленивые разделы, шрифт со своего домена, контраст цветов
по WCAG. **Грабли:** после правок Best Practices упал до 93 — Vite встроил шрифт как `data:`, а
политика безопасности (CSP) такое запрещает. Решено настройкой сборки, CSP не ослабляли.

### 4.3 Аудит безопасности

Промпт (дословно):

> Проведи аудит безопасности по OWASP Top 10 (2021). Для каждой категории: что в проекте ей
> подвержено, есть ли проблема, как проверить на практике. Особое внимание — что может сделать
> посторонний, у которого есть только публичный anon-ключ и опубликованный демо-пароль. Каждую
> находку подтверди запросом к живой базе, не ломая данных.

- **Результат:** 6 находок, все исправлены ([`security_audit.md`](security_audit.md)). Самые
  серьёзные: самостоятельная регистрация давала 30 дней подписки бесплатно; демо-пароль можно
  было сменить и «украсть» общий демо-аккаунт. Добавлены заголовки безопасности и CSP.
- **Вывод:** обе серьёзные проблемы были в настройках базы, и нашла их проверка «что можно
  сделать с публичным ключом», а не автоматический сканер.

## 5. Проблемы и решения — сводка

- **AI копирует форму исходных данных** (поле «в прошлый раз» в таблице) → задавать вопросы
  «а если…», просить связи сущностей, а не перенос моков.
- **AI делает «счастливый путь»** → в промпте явно перечислять негативные сценарии (обрыв связи,
  дубль, истёкшая сессия) — после этого они появились и в коде, и в тестах.
- **Зелёная проверка ≠ рабочий сайт** (Sensitive-переменные) → проверять результат глазами на
  проде, а в CI — содержимое сборки, а не только ответ сервера.
- **AI обещает, а не проверяет** → правило «каждую находку подтверди запросом / прогоном»; так
  агент сам нашёл ошибку в своей миграции.
- **Риск утечки и чужих данных** → разделение ролей: пароли, токены, пуш, кабинеты
  Google/Supabase/Vercel — только человек; агент работает с плейсхолдерами `<...>`.

## 6. Выводы и рекомендации

1. **Файл правил важнее длинных промптов.** Его стоит завести до первой строки кода: эксперимент
   «до/после» — 0 из 8 против 8 из 8 на одной и той же задаче.
2. **Мелкие чекпоинты с показом diff.** Не разработчик может контролировать агента, если каждый
   шаг маленький, проверяемый и объяснён простыми словами.
3. **Требовать доказательства, а не обещания:** тест, запрос к базе, скриншот, ответ
   `/api/health` с версией коммита.
4. **Спорить с первым вариантом.** Лучшие решения (представление вместо поля, отказ от
   TypeScript 7) появились после вопроса «а что если…».
5. **Агент — исполнитель, человек — владелец.** Решения о данных, деньгах, доступах и публикации
   остаются за человеком; это сделало проект безопасным без потери скорости.
