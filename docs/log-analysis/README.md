# Анализ логов с помощью ИИ

Как разбирать журнал кабинета с ИИ-агентом (Claude Code) и что он находит на типичных сбоях.

## Откуда журнал

Все записи — одна строка JSON. Поля одинаковые у сервера и браузера:

| Поле                     | Что это                                                               |
| ------------------------ | --------------------------------------------------------------------- |
| `time`                   | время в UTC                                                           |
| `level`                  | `info` / `warn` / `error`                                             |
| `scope`                  | где случилось: `health`, `client`, `client-log`                       |
| `clientScope`            | для ошибок браузера — функция кабинета (`api.saveSets`, `auth.google`) |
| `message`                | что увидела участница или что произошло                               |
| `details`                | технический код: код Postgres, HTTP-статус, текст ошибки              |
| `version`                | короткий хеш коммита сборки                                            |
| `session`                | случайный номер вкладки: записи одного человека подряд                |

Серверные записи пишут функции `/api/health` и `/api/log`. Ошибки браузера кабинет сам отправляет в `/api/log` (`navigator.sendBeacon`, не больше 20 за вкладку). Всё это собирается в **Vercel → проект → Logs** с фильтрами по уровню и тексту.

Выгрузка для разбора: Logs → фильтр по времени → Export (JSON). Или `vercel logs <адрес> --json > logs.jsonl`.

## Порядок разбора

1. **Сжать журнал:** `node scripts/summarize-logs.mjs logs.jsonl`. Скрипт считает записи по уровням и группирует одинаковые ошибки, так ИИ не тонет в повторах.
2. **Отдать ИИ сводку и сырой журнал** с промптом из раздела ниже.
3. **Проверить выводы ИИ руками**: коммит по `version`, живую базу по `/api/health`, правила доступа по `scripts/check-rls.sql`.

## Промпты

### 1. Разбор инцидента

```text
Ты — дежурный инженер веб-приложения «кабинет участницы» (React на Vercel + Supabase:
Postgres, Auth, PostgREST). Ниже сводка и журнал в JSON (одна запись в строке).

Поля: level — уровень; scope — источник (health — проверка здоровья раз в 5 минут,
client — ошибка из браузера участницы, client-log — отказ приёмника логов);
clientScope — функция кабинета; details — технический код (коды Postgres вида 23505,
PostgREST вида PGRST301, HTTP-статусы); session — вкладка; version — коммит.

Задача:
1. Восстанови хронологию: что сломалось первым, что — следствием.
2. Сгруппируй ошибки по первопричине, а не по тексту. Для каждой группы: причина,
   сколько участниц затронуто (по session), это сбой системы или ожидаемое поведение.
3. Отдели шум: ошибки, которые приложение обработало правильно (участница увидела
   понятный текст, данных не потеряно), — отдельным списком.
4. Для настоящих проблем: что проверить прямо сейчас (конкретные запросы/экраны),
   как исправить, как не допустить снова.
5. Оцени, сработал бы мониторинг (UptimeRobot смотрит на /api/health, тревога после
   2 неудачных проверок подряд).

Не выдумывай того, чего нет в журнале. Если данных не хватает — так и скажи, чего не хватает.
```

### 2. Поиск подозрительной активности

```text
Вот журнал приложения в JSON. Найди признаки злоупотребления или атаки:
всплески отказов (client-log «отклонена запись»), много 401/403 подряд с одной вкладки,
перебор адресов, неожиданные clientScope. Для каждой находки — насколько это опасно
и что сделать. Обычные ошибки пользователей не считай атакой.
```

### 3. Регрессия после выкладки

```text
Вот журнал за час до и час после выкладки версии <хеш>. Сравни частоту ошибок
по clientScope до и после. Какие ошибки появились только в новой версии?
Если есть — какие изменения кода могли их вызвать (diff приложен ниже).
```

## Проверка на типичных ошибках

Тестовый журнал `docs/log-analysis/sample-incident.jsonl`: 17 записей за 30 минут. В нём вперемешку настоящий сбой базы и обычные ситуации, которые кабинет должен обрабатывать сам. Сводка скрипта:

```text
Записей: 17 · info: 4 · error: 8 · warn: 5
  ×3  warn · client-log · отклонена запись неверного формата  (08:12:10–08:12:10)
  ×2  error · client/api.fetchProgram · 500 | canceling statement due to statement timeout  (вкладок: 2)
  ×2  error · health · есть сбой  (08:10:04–08:15:04)
  ×2  error · client/api.saveSets · TypeError: Failed to fetch  (вкладок: 1)
  ×1  error · client/api.saveSets · 500 | canceling statement due to statement timeout  (вкладок: 1)
  ×1  warn · client/api.saveMeasurement · PGRST301 | 401 | JWT expired  (вкладок: 1)
  ×1  error · client/api.saveMeasurement · 23505 | 409 | duplicate key ...  (вкладок: 1)
  ×1  warn · client/auth.google · access_denied | The user denied the request  (вкладок: 1)
```

### Что нашёл ИИ по промпту 1

Разбор Claude Code (Opus 5.5), без правок:

**Хронология.** 08:07:41 — первая ошибка `statement timeout` у участницы при сохранении подходов. 08:08–08:10 — ещё две вкладки получают тот же таймаут на загрузке программы. 08:10:04 — `/api/health` фиксирует: база не отвечает за 4 с. 08:15:04 — повтор. 08:20:04 — восстановление, но задержка базы 402 мс вместо обычных ~170: база отходит. 08:25 — норма.

**Первопричина — одна.** Около 13 минут (08:07–08:20) база не успевала выполнять запросы. Все четыре ошибки `500 | statement timeout` и два красных `health` — один инцидент. Затронуто 3 вкладки (`a1b2c3d4`, `k9j8h7g6`, `p0o9i8u7`). Сервис входа (`auth`) всё время был в порядке, значит упал не весь Supabase, а именно база. Что проверить: Supabase → Reports → Database (CPU, соединения) и Logs → Postgres за 08:05–08:20. На бесплатном тарифе это похоже на нехватку ресурсов или долгий запрос.

**Мониторинг сработал бы.** Две неудачные проверки подряд (08:10 и 08:15) — тревога в 08:15, через ~8 минут после первой жалобы в журнале. Чтобы узнавать раньше, нужен интервал в 1–2 минуты. Он есть только на платном тарифе UptimeRobot.

**Не проблемы — кабинет отработал правильно:**
- `PGRST301 JWT expired` — сессия участницы истекла, ей показано «войдите заново». Штатно.
- `23505 duplicate key` — второй замер на ту же дату, ей объяснили, что делать. Штатно. *Та же вкладка `z5y4x3w2` двумя минутами раньше получила истёкшую сессию. Видимо, после повторного входа участница отправила форму дважды. Кандидат на улучшение: блокировать кнопку до ответа сервера. Проверить в `MeasurementsPage`.*
- `Failed to fetch` ×2 с одной вкладки за 2 секунды — у одной участницы пропал интернет. В базе в это время всё в порядке. Штатно, подходы сохранены на устройстве.
- `access_denied` у Google — участница сама нажала «Отмена».

**Подозрительное:** три отказа `client-log` за 0,2 секунды. Это не браузер кабинета: он шлёт корректный формат. Кто-то вручную или скриптом бьёт в `/api/log`. Приёмник всё отклонил, вреда нет. Если повторится массово — ограничить частоту на уровне Vercel Firewall (правило rate limit на `/api/log`).

### Проверка выводов

- ✅ Хронология и группировка сверены по файлу вручную. Все 8 предупреждений и ошибок разнесены верно.
- ✅ Правило «тревога после двух неудач» соответствует настройке монитора, см. `integration_documentation.md`.
- ✅ Кнопка «Сохранить замер» на время запроса уже блокируется (`disabled={pending}` в `MeasurementsPage`, строка 113). Значит, дубль — это две разные отправки, а не двойной клик. ИИ предложил гипотезу и честно пометил её «проверить». Проверка её не подтвердила.
